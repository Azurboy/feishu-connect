# 第二阶段调研：让云端 personal agent 连接飞书

调研日期：2026-09-29。  
范围：飞书云文档、知识库；用户已明确首版优先这两类内容。  
交付：[开发规格 v0.1](./SPEC_v0.1.md)。本轮未连接个人账号、部署服务、申请上架或联系平台。

## 1. 结论

**技术路线成立：提供带浏览器授权的远程 MCP 服务，让云端 agent 按用户身份搜索和读取飞书。** 用户无需在自己的电脑上安装 CLI。已有项目验证了这类工程形态，值得复用；可做的产品价值是连接、授权和日常使用体验。

但“有远程 MCP”与“在某个产品的应用目录里一键连接”之间，仍有两道门槛：

1. **agent 产品开放什么入口**：是否允许自定义服务、接受哪种授权、是否需要平台审核。
2. **飞书允许谁安装和授权这个应用**：自建应用通常限同一企业；跨企业服务涉及商店应用发布及租户安装。

因此建议先做一个小型的 **Feishu Connect：云文档与知识库只读连接器**。以有明确开放接口的客户端验证核心；Cue 和 Muse 仍是目标产品，单独记录平台接入状态。不能用 Manus 已支持 MCP 来宣布 Cue 已兼容。

## 2. 飞书并非只有本地 CLI

### 2.1 官方现状比“本地 CLI vs 国外连接器”更复杂

| 官方能力 | 本轮核对到的状态 | 对产品的影响 |
| --- | --- | --- |
| [lark-cli](https://github.com/larksuite/cli) | 本地 CLI 是一种运行方式；有服务器可执行环境时也可以部署在云端 | 问题是用户安装/授权体验与云端客户端入口，不是 CLI 技术上只能在用户电脑运行 |
| [官方 OpenAPI MCP](https://github.com/larksuite/lark-openapi-mcp) | 支持 stdio、Streamable HTTP 等；其配置文档仍把用户 OAuth 的 streamable 模式限于 localhost | 开源程序能提供 HTTP，不代表已经具备可直接公开运营的多用户 OAuth 服务 |
| [旧远程 MCP 配置](https://open.feishu.cn/document/mcp_open_tools/call-feishu-mcp-server-in-remote-mode) | 文档标记不再更新，引导使用新版 | 不能把旧教程当当前产品说明 |
| [新版个人 MCP](https://open.feishu.cn/document/mcp_open_tools/end-user-call-remote-mcp-server) | 内测；目前云文档场景；个人托管 MCP Token 链路将逐步下线；自 2026-02-24 起新链接有效期为 7 天 | 不适合作为长期产品的核心依赖；官方未在此给出确定的最终下线日期 |
| [远程 MCP 工具列表](https://open.feishu.cn/document/mcp_open_tools/supported-tools) | 包含文档搜索、读取、知识库目录以及部分写入工具；不等于全飞书 API | 说明有明确使用场景，也说明不能以一个“飞书连接成功”覆盖所有业务 |

飞书网页正文在普通网页抓取中经常为空。本轮按官方 [llms 索引](https://open.feishu.cn/llms.txt) → 模块索引 → 官方 `.md` 正文核对，以上关于个人 MCP 的状态来自最新正文，而非第三方转载。入口页可通过在 URL 后添加 `.md` 读取对应的官方 Markdown 版本。

OpenAPI MCP 的限制原文位置：[Service Deployment / OAuth Limitation](https://github.com/larksuite/lark-openapi-mcp/blob/main/docs/usage/configuration/configuration.md)。这是当前文档描述，本轮没有运行该软件去确认行为是否已超前于文档。

### 2.2 当前“容易连接”的差距是什么

不是缺少一套飞书 API，而是缺少对普通用户稳定交付的组合：

- 已托管且长期可访问的服务。
- 个人用户浏览器登录，身份与内容权限对应正确。
- Token 自动续期，失效后能恢复。
- 目标客户端支持并能发现该服务。
- 组织已允许安装/使用应用，用户知道授权了哪些数据。

这几件事属于产品本身。把 `lark-cli` 包上一层 HTTP，但仍要求每位用户建应用、复制 secret，改善会有限。

## 3. 各目标产品的真实入口

下表是**文档核验状态**，不是本项目的端到端兼容测试结果。账号权限、套餐和产品版本还需要实际检查。

| 产品 | 已确认 | 未确认 | 建议路径 |
| --- | --- | --- | --- |
| ChatGPT | 官方支持通过开发者模式连接远程 MCP，支持 OAuth；公开插件有单独发布流程 | 用户账号是否开放该入口；本项目实际授权、工具调用 | 首个标准 OAuth 客户端验证对象 |
| Manus | 官方明确提供 Custom MCP Servers；支持输入 HTTPS 服务地址及所需认证信息 | 本项目的 OAuth 自动发现/刷新是否在实际客户端完整支持 | 第二个远程客户端；先实测授权，不能只测 tools/list |
| Cue（Manus） | 官方产品介绍确认其为个人 agent 应用 | 未找到足以确认 Cue 可自助添加任意 MCP 的官方说明；是否继承 Manus 的连接器配置未知 | 先核对实际产品入口或平台明确答复，不能用 Manus 兼容代替 |
| Muse（Meta） | 有官方 Connector Platform，提交后进行功能、安全及法律要求审查，通过后进入目录 | 公共页面未给出任意用户直接添加 MCP 的完整协议、OAuth 参数及自助入口 | 准备一个可测试服务和演示，再按官方入口申请；不承诺审批结果 |

来源：[OpenAI 连接与测试](https://developers.openai.com/plugins/deploy/connect-chatgpt) · [OpenAI 授权](https://developers.openai.com/plugins/build/auth) · [Manus 自定义 MCP](https://manus.im/docs/integrations/custom-mcp) · [Manus 产品目录中的 Cue 介绍](https://manus.im/blog/product) · [Muse Connector Platform](https://muse.ai/platform)

**远程 MCP 是可复用的底座，不是所有 agent 都承诺开放的万能入口。** 对没有入口的产品，额外写一个网关不会凭空增加它的连接器能力。登录网页、粘贴文档、邮件转发可以完成个别任务，但不计入本项目的正式集成验收。

### Slack 的体验可以学，但也有平台前提

Slack 官方提供 Streamable HTTP MCP、OAuth 和应用身份；文档要求由已注册应用承载，管理员可控制集成，公开使用涉及其应用分发规则。用户看到的简单授权，是这些准备已由平台和服务商完成的结果。[Slack MCP 官方说明](https://docs.slack.dev/ai/slack-mcp-server/)

这不证明 ChatGPT 内置 Slack 一定使用该 MCP 实现；我们参考的是授权、身份、发现和分发模式，不臆测内置连接器的内部实现。

## 5. 飞书授权和跨企业分发是关键门槛

### 5.1 两种身份不能混用

- `user_access_token`：代表授权用户读取其可访问的数据，适合 personal agent。
- `tenant_access_token`：代表应用，不等于当前用户；不能在用户授权失败后自动切换为应用身份继续读。

有效访问还同时取决于应用权限、用户授权和资源自身权限。用户能在飞书里看到某份文档，不代表任何应用自动就能通过 API 读到它。[飞书开放平台概述](https://open.feishu.cn/llms.txt)

### 5.2 “每人建应用”与“登录即用”的区别

| 模式 | 管理员/运营者工作 | 普通用户工作 | 适合阶段 |
| --- | --- | --- | --- |
| 每个人自己部署、自己建应用 | 分散给每个人 | 配置域名/secret/OAuth | 开源开发者使用；不满足主产品的便利目标 |
| 一个组织内的托管实例 | 管理员配置一个自建应用、权限、可用范围和服务 | 添加地址、浏览器授权 | 首批 3–5 人验证 |
| 跨企业的公共连接器 | 服务商准备商店应用、发布/安装流程及目标平台分发 | 所属租户允许安装后授权 | 更接近 Slack 式的公众产品，需要后续平台流程 |

自建应用只能在同一企业内发布使用，不能拿自己企业的 app ID 当成任意飞书用户都可登录的公共应用。[飞书应用类型](https://open.feishu.cn/document/home/app-types-introduction/robots-web-applications-and-mini-programs)

组织管理员是否需要审批、应用能否安装，都应按租户设置显示。我们可以减少用户操作，但不能承诺绕过这些限制。

### 5.3 Token 续期需要做实

官方最新换取 token 文档已引导 v3 端点并说明 PKCE。旧授权页面中仍有“PKCE 暂配 v2”的表述，和新 token 文档存在更新不同步；实现以最新端点文档加实际联调为准，不照搬旧脚本。

`offline_access` 才能获得刷新能力；refresh token 为一次性轮换，必须串行更新持久状态。到期或撤销后要求重新登录，不能承诺永久免登录。官方还规定授权超过 365 天需要重新授权。[获取 token v3](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3) · [刷新 token v3](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/refresh-user-access-token-v3)

## 6. 建议的产品位置

工作名：**Feishu Connect**。定位：

> **让你的 AI 助手，读到飞书里的工作资料。**

首版只做三个用户任务：按关键词找文档、读取指定文档、浏览知识库目录。原文按需读取、返回来源链接；理解和写作交给用户现有的 agent。

推荐先交付“组织内免安装的托管连接器”，同时保留可自行部署的代码。面向公众的跨企业授权作为第二阶段后半段的分发里程碑，而不是假定已经解决。

产品价值应通过这些问题验证：

- 管理员准备好后，普通用户能否只用浏览器完成连接？
- 能否在熟悉的 agent 中找出并读到真正的飞书原文？
- 几天不用后能否恢复，撤销授权后是否确实停止访问？
- 失败时能否分清客户端入口、应用可用范围、缺少 scope 和资源权限？

不需要另一套聊天产品、RAG 知识库、内容同步仓库或通用国内应用市场。将来接钉钉、企业微信时，可复用授权和工具交付经验；各平台的权限与分发仍要单独调研。

## 8. 需要诚实保留的未知项
